# ADR-0032 · «Путь Посла»: личный опыт посла, семь рангов и одеяния цивилизаций

Status: accepted (решение владельца «THE ENVOY'S PATH», 2026-11-13). Начисление «+5 за решённую проблему»
выключено до решения владельца (см. «Открытые вопросы»); решено в ADR-0035 — подтверждает автор.

## Контекст

На карте Великого Содружества открытые обращения — послы, идущие к Совету (ADR-0011, ADR-0021). Замки растут
только от внедрённых идей (`xp_awards`, ADR-0012). Владелец решил дать каждому сотруднику его символического
посла, облик которого развивается по мере **доказанной** пользы его обращений. Принцип: «Не количество
отправленных посланий определяет величие посла, а доказанная польза».

## Аудит: что было

| Нужно | Было в `main` | Добавлено |
| --- | --- | --- |
| Посол на карте | `kingdom.ts`: открытые обращения из `idea_overview` под RLS; `EnvoyMark` в `Kingdom.tsx` | Ранг и цивилизация посла, имя отправителя, одеяние по рангу |
| Подтверждённое внедрение | `xp_awards.kind = 'implementation'` (триггер при переходе в `impact_verification`) | Начисление послу из этой же строки |
| Подтверждённый эффект | `effect_approvals` (только decision owner, один раз) и измерения `verification_evidence` (ADR-0031) | Начисление послу только при бонусе > 0 **и** измеренном улучшении |
| «Проблема решена» | Решения `merge / reject / close`; «решено» = путь через внедрение | Отдельного проверяемого события нет — начисление выключено |
| Атрибуция | `coalesce(raised_by, author)` — «чей вопрос» (ADR-0007) | Тот же получатель, один на обращение |
| Уведомления | `notifications`, записи только через функции базы | Событие `envoy_rank_up` |
| Личная карточка | `Person.tsx` / `district.person` | Раздел «Мой посол» / «Посол» |
| Цивилизации | Реестр из пяти: Камелот, сёгунат, ханство, царство, Монгольская держава. Рима нет | Одеяния для всех пяти; Рим не создаётся |

## Решение

1. **Отдельный журнал.** `envoy_xp_awards` — только для добавления, RLS, запись только триггерами базы
   (`SECURITY DEFINER`, роль приложения права INSERT не имеет). `xp_awards` замков не читается для записи и не
   меняется: личный опыт и опыт замка — разные суммы одного факта, ни одна не начисляется из другой повторно.
2. **Подтверждённые события и стартовые значения** (столбцы `organizations.envoy_xp_*`, централизованно;
   правила — в `platform/domain/envoy.ts`):

   | Событие | XP | Основание (`source_type`) |
   | --- | ---: | --- |
   | Отправил обращение, посол прибыл, Король принял посла | 0 | — |
   | Проблема содержательно решена (`resolution`) | 5 | **выключено**: проверяемого события нет |
   | Подтверждено внедрение (`implementation`) | 20 | строка `xp_awards` kind = implementation |
   | Подтверждён измеримый положительный эффект (`effect`) | 30 | `effect_approvals` с бонусом > 0 **и** завершённая проверка `impact`, где хотя бы одна метрика улучшилась по правилам ADR-0031 |

   Эффект проверяется в базе тем же строгим правилом, что и `effect.ts`: последнее «до» с названным
   направлением, «после» не раньше него, та же единица, отметка сопоставимости, изменение в нужную сторону.
   Триггеры срабатывают на подтверждение бонуса и на завершение проверки `impact` — что бы ни случилось
   вторым, начисление одно.
3. **Атрибуция.** Получатель — тот, чей это вопрос: `raised_by`, если обращение записано от имени
   сотрудника, иначе автор. Исполнитель и ответственный за решение личный XP за чужое обращение не получают;
   полная сумма не раздаётся каждому участнику.
4. **Без накрутки.** Уникальность `(idea_id, event_kind)`: одно обращение — одно начисление каждого вида,
   повторный запрос, повтор шага и параллельная транзакция дубля не создают. Начисления одному человеку
   сериализуются `pg_advisory_xact_lock`, поэтому переход порога не теряется при параллельных внедрениях.
   Ничего не начисляется за количество обращений, вход, комментарии, аудиенцию, отклонение, закрытие.
5. **Ранги** (пороги в `organizations.envoy_rank_thresholds`, проверка `app_envoy_thresholds_ok`):
   I Гонец 0 · II Вестник 20 · III Доверенный посланник 60 · IV Герольд 140 · V Посол Совета 280 ·
   VI Великий посол 500 · VII Посол Великого Содружества 800. Ранг считает сервер из суммы журнала; выше VII не
   растёт, XP продолжает учитываться; сезонного сброса нет.
6. **Повышение — подтверждённое событие.** `envoy_rank_ups (membership_id, rank)` уникально, пишется в той же
   транзакции, что начисление; в журнал аудита — `envoy.rank_up` без пользовательского текста. Уведомление
   `envoy_rank_up` идёт владельцу посла через общую таблицу уведомлений и остаётся непрочитанным, пока он не
   откроет его — карточка «Ваш посол достиг ранга …!» показывается и после следующего входа. Просмотр
   анимации ничего не начисляет: отметка «прочитано» — существующий маршрут `notifications/read`.
7. **Одеяния.** Описание частей (`web/src/lib/envoy-outfits.ts`) — данные по цивилизации и рангу, рисует их
   `EnvoyFigure` (SVG). Фигура без головы и лица: головной убор над высоким воротником. Каждый следующий ранг
   добавляет новые предметы, а не цвет. Набор цивилизаций берётся из реестра; цивилизация — подразделения
   сотрудника, поэтому смена стиля меняет одежду, но не XP. На карте: I–II простой силуэт, III–IV знаки,
   V–VI церемониальные детали, VII — знак Содружества.
8. **Ранг не даёт прав.** Ни один маршрут не читает ранг для проверки полномочий; RLS-политики и
   `authorize` не менялись. Ранг виден там, где виден сам человек (карточка — сотрудникам организации).
9. **Без личных рейтингов.** Нет таблицы лидеров людей: ранг виден у посла на карте и в карточке, рейтинг
   остаётся у замков.

## Ограничения (не скрываются)

- Графика — программная отрисовка SVG, не иллюстрации художника; историческая достоверность костюмов —
  стилизация по общим признакам эпохи, не реконструкция.
- Начисления за события до этой миграции восстановлены из `xp_awards` и измерений с исходными датами;
  уведомлений о таких «исторических» повышениях нет (иначе после обновления пришла бы пачка карточек).
- Мобильная проверка — эмуляция вьюпорта в браузере сценария, не реальное устройство.
- 3D-город: геометрия гонцов (three.js) не менялась — ранг и отправитель показаны в карточке над гонцом.
  Одеяния по рангу видны на схеме города, в «Моём после», в «Посольстве» и в карточке повышения.

## Открытые вопросы (решение владельца)

- **+5 за решённую проблему.** В модели нет события «проблема подтверждённо решена», отличного от
  внедрения: `close` — административное закрытие (дубликат), `reject` — отклонение, `merge` — решение
  внедрять. Предложение: для `kind = 'problem'` после внедрения автор подтверждает «проблема решена»
  (не ответственный), тогда +5. Пока столбец `envoy_xp_resolution` хранит значение, но писателя нет.
- **Отказ от атрибуции после начисления** (`declineAttribution`). Журнал только для добавления; начисление
  остаётся у того, кому было выдано. Сторнирующая запись — отдельное решение.
- **Эффект без измерений** по-прежнему подтверждается для замка (ADR-0031), но личных +30 не даёт.
- Настройки значений XP и порогов — пока только миграцией; экрана администратора нет.

## Проверки

- `test/platform/envoy.test.ts` — 17 тестов на PostgreSQL: начальный ранг I; 100 жалоб, комментарии,
  отклонение, закрытие и отозванный запрос — 0 XP; аудиенция у Короля — 0 XP; внедрение +20 один раз
  (повтор, тот же ключ, пересохранение); эффект +30 один раз при любом порядке «одобрение / завершённый замер»;
  без замера, при ухудшении и при нулевом бонусе — нет; атрибуция «от имени»; параллельные запросы (тест
  падает, если убрать `pg_advisory_xact_lock`, — проверено); повышение записано, ждёт непрочитанным, чтение
  ничего не начисляет; журнал неизменяем даже владельцем схемы; смена цивилизации — одежда, не XP; гость и
  чужая организация; черновики Лаборатории не на карте; ранг VII не даёт прав; карта не раскрывает id и XP.
- `test/platform/envoy-outfits.test.ts` — 4 теста без базы: цивилизации = реестр (Рима нет), семь разных
  одеяний в каждой, каждый ранг добавляет предметы и новый плащ, у одного ранга в разных цивилизациях — своя
  одежда и головной убор.
- `web/e2e/envoy-flow.mjs` (`npm run demo:envoy`) — 8 шагов на свежих демо-данных, снимки в `docs/demo/envoy/`:
  карточка повышения после входа и «Пропустить», подача → посол на карте в одеянии ранга, внедрение и
  измеренный эффект → ранг III после следующего входа без блокировки навигации, «Мой посол» с основаниями,
  отказ в правах, телефон 390×844, облегчённый режим и `prefers-reduced-motion`.

Все прогоны локальные (2026-11-13, macOS, PostgreSQL 16 в docker, Chromium Playwright). GitHub CI —
только после реального зелёного прогона.
